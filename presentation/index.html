Abstract

When data travels over a network, it is split into small pieces called packets. Some packets never reach the other side. This is called packet loss.

 

UDP, a common way of sending data, does not notice or fix this loss. Our project adds three things on top of UDP: numbering every packet, a reply for every packet received, and resending packets that get no reply.

 

We also build a network in Mininet with a main path and a backup path. If the main path fails, traffic is moved to the backup path automatically.

Our idea in one line

Resending fixes small losses.

Rerouting fixes big failures.

Small losses → fixed by our Python programs

Big failures → fixed by our Mininet network

Problem

Statement

UDP sends packets without checking if they arrived. If 10% of packets are lost, 10% of the data is gone and nobody knows. If a link breaks, all traffic stops.

 

We need a way to notice the loss, get the data back, and keep traffic flowing.

Objective 1 – Detect

Number every packet so the receiver can tell when one is missing

Objective 2 – Recover

Reply for every packet received, and resend any packet that gets no reply

Objective 3 – Reroute

If the main path fails, move traffic to a backup path and measure how long it takes

TCP vs UDP

TCP

Transmission Control Protocol

●  Checks that every packet arrived

●  Resends lost packets by itself

●  Reliable but slower, like registered post

UDP

User Datagram Protocol

●  Just sends packets, no checking

●  Lost packets are simply gone

●  Fast but unreliable, like a postcard

Why we use UDP and not TCP

TCP already fixes packet loss on its own, so there would be nothing left for us to build or show. UDP has no protection, so we add our own detection (packet numbers) and recovery (ACKs and resending) and prove they work. Real apps like video calls, online games and live streaming also use UDP, because speed matters more than perfect delivery.

Congestion

Too much traffic. The router is full, so new packets are thrown away.

Link failure

A cable or port stops working. Packets have nowhere to go.

Noise / errors

Signal noise damages the data. The damaged packet is thrown away.

Routing loop

The packet goes round in circles until its hop limit (TTL) runs out.

Why Do Packets

Get Lost?

These four problems happen in real networks every day.

 

In our project we create two of them on purpose, random loss and a broken link, so we can test whether our solution detects and fixes them.

Network

Architecture

Server A (h1) on Network A 10.1.1.0/24 is the sender. Server B (h2) on Network B 10.2.2.0/24 is the receiver. Data normally takes the main path s1 → s2 → s4. We add 10% loss on the s1–s2 cable on purpose.

 

Each switch has a job: s1 decides the path, s2 is the main route, s3 is the backup route, and s4 is where both paths join.

 

If the main path fails, our path monitor changes the rules in s1 and s4, so data goes through s3 instead.

Small losses – our Python programs

●  Every packet gets a number: 0, 1, 2, 3 ...

●  Receiver gets 14 then 17, so 15 and 16 are missing

●  Receiver replies "got it" (ACK) for each packet

●  No reply in 0.2 seconds → sender sends it again

Big failures – our Mininet network

●  Monitor keeps checking the main path

●  It sends test pings to measure loss

●  Link down or loss above 50% → failure found

●  Switch rules changed → traffic goes via s3

How It

Works

Think of page numbers in a book. If page 14 is followed by page 17, you know pages 15 and 16 are missing. We do the same with packets.

 

The sender then sends the missing packets again. If the whole path breaks, we switch to the backup path.
