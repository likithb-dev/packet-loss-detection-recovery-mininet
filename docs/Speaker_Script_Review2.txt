[WHEN #2 TURNS RED] Packet 2 was lost on the cable between s1 and s2. Right now, nobody knows.

## WHAT'S ACTUALLY HAPPENING (for you)
• Detection (udp_receiver.py): Server B remembers the highest number it has seen. Packet 3 arrives, the highest was 1, so it checks the numbers in between and finds 2 never came.
• Recovery (udp_sender.py): Server A notes when it sent each packet. No ACK within the timeout (0.2 s in the real code, 85 ms here) → send it again.
• Packets 4 and 5 leave late because Server A only allows 4 packets waiting for a reply at once (the "window"). 8 in the real code; 4 here so it is easy to see.
• The animation is slowed down about 100× so people can follow it. Times shown are network time.

## WHAT'S ACTUALLY HAPPENING (for you)
• A switch rule is one line: "packets in on port 1 → send out port 2". In s1: port 1 = Server A, port 2 = s2 (main), port 3 = s3 (backup). Rerouting = changing "out 2" to "out 3" with ovs-ofctl. s4 gets the same change so ACKs also come back via s3.
• The monitor (mininet_reroute.py) checks every 0.1 s: is the s1–s2 cable up, and do test pings get through? Down, or more than 50% loss → reroute.
• 6 and 7 were lost because they were on the cable in the few ms before the monitor reacted. Recovery fixes those, so the two methods work together.

## SAY: our real results
[CLICK run_tests.py] These numbers are not from the animation. They come from our real test run on the laptop: 200 packets per run, 3 runs each, averaged.
Test 1: plain UDP delivered 95.8% at 5% loss, 87.7% at 10%, and only 76.7% at 20%. Our method delivered 100% every time. The price is resends: about 24, 48 and 102.
Test 5: every timeout delivered 100%. A 0.1-second timeout finished in 2.5 seconds, 0.2 in 5.3, and 0.5 in 12.8. A shorter wait recovers faster, as long as it is longer than the time a reply takes to come back.

════════ Q&A ════════
Krithik takes each question first. Concepts (UDP, ACK, timeout) → Lahaarika. Network (switches, rerouting) → Likhit. Results → Krithik.
Why 4 switches? s1 decides, s2 main route (lets us test a switch failure), s3 backup with nothing shared, s4 joins the paths.
How does rerouting happen? The monitor runs ovs-ofctl add-flow to change s1 and s4 from output port 2 to port 3 (OpenFlow).
Why two different networks? To act like two real separate sites; each server reaches the other network through its switch.
Why UDP, not TCP? TCP already recovers by itself; we build recovery on UDP to show how it works.
What if an ACK is lost? The sender times out and resends; the receiver gets a duplicate, ignores it and ACKs again.
Is this real? The screen replays our code's logic and output so it can be watched slowly. The real programs run in our Ubuntu VM (sudo python3 live_demo.py) and on the laptop (run_tests.py).
If nobody knows: "We will test that and include it in our report." Never guess.
